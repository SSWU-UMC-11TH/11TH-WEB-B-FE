### 1. Branch Rule

개인 메인 브랜치는 **본인의 닉네임**으로 생성합니다.

``` text
jay
```

주차별 미션은 개인 브랜치에서 새로운 작업 브랜치를 생성하여 진행합니다.

``` text
닉네임/week번호
```

예시

``` text
jay/week01
jay/week02
```

작업 흐름은 다음과 같습니다.

``` text
main
 ↓
jay
 ↓
jay/week01
```

> 🚨 **main 브랜치에 직접 Push하지 않습니다.**\
> 반드시 본인의 브랜치 및 주차별 작업 브랜치를 사용해주세요.

------------------------------------------------------------------------

## 2. Commit Rule

### 🚨 통커밋 금지

주차 미션을 모두 완료한 뒤 한 번에 Commit하는 방식은 지양합니다.

**기능 개발 및 작업 단위로 Commit을 나누어 진행해주세요.**

``` text
❌ feat: 1주차 미션 완료

✅ feat: 회원가입 기능 구현
✅ feat: 로그인 기능 구현
✅ fix: 로그인 예외 처리 수정
```

하나의 Commit에는 **하나의 작업 목적**만 포함하는 것을 권장합니다.

### Commit Convention

| Convention | 설명 |
| :---: | --- |
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 및 오류 수정 |
| `refactor` | 코드 리팩토링 |
| `docs` | README 등 문서 수정 |
| `test` | 테스트 코드 추가 및 수정 |
| `chore` | 설정 및 내부 파일 수정 |

------------------------------------------------------------------------

## 3. Issue / Pull Request

주차별 미션 진행 시 **Issue와 Pull Request는 필수로 생성합니다.**

-   작업 시작 전 **Issue 생성**
-   미션 완료 후 **Pull Request 생성**
-   Issue / PR 작성 방식은 제공된 템플릿을 사용해주세요.
-   코드 리뷰 및 수정 사항을 반영한 후 Merge합니다.

PR 진행 방향

``` text
주차별 작업 브랜치 → 개인 브랜치
```

예시

``` text
jay/week01 → jay
```

------------------------------------------------------------------------

## 🔄 작업 진행 방식

1.  개인 브랜치에서 최신 내용을 Pull합니다.
2.  해당 주차 작업 브랜치를 생성합니다.
3.  미션을 진행하며 **기능 단위로 Commit**합니다.
4.  작업 내용을 본인의 작업 브랜치에 Push합니다.
5.  Issue / PR 규칙에 맞게 PR을 생성합니다.
6.  리뷰 및 수정 후 개인 브랜치에 Merge합니다.
7.  다음 주차에는 최신 개인 브랜치에서 새로운 작업 브랜치를 생성합니다.

# Week 2 - React 컴포넌트 및 상태 기반 UI 구성

## 핵심 키워드

### React 컴포넌트와 JSX

- JSX는 JavaScript 안에서 HTML-like 문법을 쓰게 해주는 문법입니다. JSX는 실제로는 함수 호출과 객체로 변환되어 컴포넌트의 UI를 선언적으로 표현합니다.
- 컴포넌트는 UI를 작은 단위로 나눠 재사용성과 가독성을 높입니다. 역할 단위로(헤더, 리스트, 카드 등) 분리하면 유지보수가 쉬워집니다.
- 조건부 렌더링은 `&&`, `?:` 연산자나 별도의 렌더 함수로 처리합니다. 리스트 렌더링은 `map()`을 사용하고, 각 항목에 고유한 `key`를 주어 리액트가 효율적으로 업데이트하도록 합니다.

### props와 단방향 데이터 흐름

- `props`는 부모가 자식에게 전달하는 읽기 전용 데이터입니다.
- 데이터는 부모 → 자식 방향으로 흐르며, 이 단방향 흐름 덕분에 컴포넌트 상태를 예측하기 쉬워집니다.
- TypeScript로 `props` 타입을 정의하면 컴파일 타임에서 실수를 잡을 수 있어 안전합니다.

### 상태와 리렌더링

- 일반 변수는 변경되어도 리액트가 UI를 갱신하지 않지만, `state`로 관리하면 변경 시 자동으로 리렌더링이 발생합니다.
- `useState`는 컴포넌트의 상태를 관리하며, 상태를 직접 수정하지 않고 항상 새 객체/배열을 만들어서 업데이트해야 합니다.
- 배열/객체를 업데이트할 때는 `map`, `filter`, 전개 연산자(...) 등을 사용합니다.
- 이전 상태를 기반으로 업데이트할 때는 `setState(prev => newState)` 형태의 업데이터 함수를 사용하면 안전합니다.

### 상태 공유와 Context

- 여러 컴포넌트에서 같은 상태가 필요하면 상태를 공통 부모로 끌어올려서 단일 출처(Single Source of Truth)를 구현합니다.
- 간단한 경우는 `props` 전달로 충분하지만, 여러 단계에 걸쳐 전달해야 하면 `Context`를 고려합니다.
- 모든 것을 Context로 관리하면 추적이 어려워지고 성능 문제가 생길 수 있으니 꼭 필요한 경우에만 사용합니다.

## 미션 기록

- 영화 타입과 더미 데이터를 파일로 분리 (`src/types/movie.ts`, `src/data/movies.ts`)
- Header, MovieGrid, MovieCard, Pagination 컴포넌트 분리 (`src/components`)
- `map`과 `props`를 이용해 영화 10편 렌더링
- `useState`로 영화 목록 상태 관리 및 id 기준 북마크 토글 구현
- 기존 배열을 직접 수정하지 않고 `map`과 전개 문법 사용

## 트러블슈팅

### 문제
프로젝트 초기 구성 후 asset 경로가 데이터와 일치하지 않아 이미지가 보이지 않았습니다.

### 원인
미션에 예시로 제공된 `posterPath`가 `/images/movies/...` 형태였으나, 실제 제공된 에셋은 `/public/images/` 루트에 바로 위치해 있었습니다.

### 해결
`src/data/movies.ts`의 `posterPath`와 `backdropPath`를 실제 존재하는 파일 경로(`/images/<file>.jpg`)로 수정했습니다.

### 배운 점
프로젝트를 세팅할 때는 실제 파일 위치를 먼저 확인하고 경로를 맞추는 것이 중요합니다.
